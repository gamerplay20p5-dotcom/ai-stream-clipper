## O que o repositório exige (revisão da `main`)

1. **Bloqueio real, já corrigido:** a API 0.8.0 não sobe em produção sem `ASC_PUBLIC_ORIGIN`, e o Compose da 210
   recusa o arquivo sem essa variável. O `asc-ctl` 1.2.0 instalado na 210 **não aceita** essa variável no
   `env-install`. A correção é o `asc-ctl` **1.2.1**, que muda só o número da versão em relação ao arquivo da `main`.
   Ele precisa ser instalado **somente na 210**. Na 201, na 206 e na 212 nada muda.
   - SHA-256 do `asc-ctl` 1.2.0 (instalado): `84a8a2bad2dfa62c7aa26959c00742f6fc68b0d67e5bd9b304da63e2a1acdf09`
   - SHA-256 do `asc-ctl` 1.2.1: `ff4539e7497f874cc81789967b0ed35026eef0b9710351143810ae291c239533`
2. **Migrações 0015 a 0019:**
   - Todas são aditivas e as colunas novas têm valor padrão, então nenhum dado existente muda.
   - Os canais existentes ficam com `hts_monitoring = true` e o comportamento da HTS não muda.
   - O Alembic deste projeto roda **toda a cadeia numa única transação** (`migrations/env.py`). No PostgreSQL,
     qualquer erro desfaz tudo e o banco continua na 0014.
   - A 0018 recusa rodar se algum canal tiver duas sessões `live`.
3. **Dependências:**
   - Nenhum pacote Python novo.
   - A imagem `app` passa a incluir `commercial/catalog.json`, já previsto no `app.Dockerfile`.
   - O dashboard continua sendo compilado dentro da imagem `app`.
4. **Serviço comercial** (site de vendas, Stripe e InfinitePay): **não entra nesta implantação**. Não há serviço
   dele no Compose de produção, e `ASC_BILLING_SECRET` e `ASC_COMMERCIAL_URL` não são configurados. Por isso o
   vínculo de assinaturas fica desligado. As contas de clientes só podem receber planos de **cortesia** no painel
   da HTS.
5. **Workers:** todos os serviços passam para a mesma tag 0.8.0. Não misture versões: a captura compartilhada
   muda o comportamento do worker de captura.
6. **Cuidado na 210:** `compose up api` também liga o `asc-postgres` **antigo** da 210 (`depends_on`). Ele não
   recebe conexões (a API usa a 212). Se estava parado antes, volte a pará-lo no fim (passo 6.4).

## Rollback para a 0.7.6 (depois da migração)

A 0.7.6 **não sobe num banco na 0019**: o Alembic dela não conhece essas revisões. Por isso, primeiro volte o
esquema com a imagem 0.8.0 e só depois troque a imagem.

1. Pausa e parada: `publish-pause on`, depois pare os workers na 206, na 201 e na 210, **deixando a API 0.8.0 ligada**.
2. Confira que nenhum dado de cliente seria perdido (na 212):
   ```bash
   q "select (select count(*) from publish_accounts where owner_id is not null) + (select count(*) from publications where owner_id is not null) + (select count(*) from channel_monitors) + (select count(*) from account_subscriptions) + (select count(*) from courtesy_grants)"
   ```
   **Precisa dar 0.** O normal nesta implantação é dar 0, porque não há vendas nem clientes ativos. Se der mais que
   0, não faça o downgrade: ele apagaria a ligação desses registros com os clientes. Me procure antes.
3. Volta do esquema:
   ```bash
   sudo asc-ctl exec asc-api -- clipper migrate --downgrade 0014
   ```
   Depois, `q "select version_num from alembic_version"` deve dar `0014`.
4. Volta da imagem:
   - na 210: `sudo asc-ctl set-tag 0.7.6`, `compose up --gpu api` e depois os workers;
   - na 206 e na 201: `set-tag 0.7.6` e `compose up`;
   - por fim, `publish-pause off`.
5. O `ASC_PUBLIC_ORIGIN` pode ficar: a 0.7.6 não usa essa variável. O `asc-ctl` 1.2.1 também pode ficar.

### Quando restaurar o backup

Só restaure se:
- o downgrade falhar no meio;
- houver dados antigos perdidos ou corrompidos (linhas "<" no `diff` de contagens);
- houver um problema que o downgrade não resolva.

A restauração apaga tudo o que foi gravado depois do backup. Com as publicações pausadas, isso fica restrito aos
minutos da janela.

Na 212, com **todos** os serviços do ASC parados (inclusive a API):
```bash
sudo asc-ctl backup-db                                   # cópia do estado com problema, para análise
sudo asc-ctl exec asc-postgres -- psql -U asc -d asc -v ON_ERROR_STOP=1 -c "drop schema public cascade; create schema public"
sudo asc-ctl db-restore ~/backups/<arquivo do passo 2.4>.sql.gz
q "select version_num from alembic_version"              # 0014
q "$CNT" | diff ~/pre-0.8.0/contagens-antes.txt - && echo "IGUAL AO BACKUP"
```
Depois, religue a 0.7.6, como no passo 4 acima.

## English summary

Deploy plan for v0.8.0 (`main` with PRs #23–#25, homologated tree `af810ed`). It was prepared, not executed, and
uses only the existing tools (`asc-ctl`, `asc-send`, `backup-db`, per-server Compose files).

- **Real blocker, fixed:** the 0.8.0 API needs `ASC_PUBLIC_ORIGIN`, but the installed `asc-ctl` 1.2.0 rejects it.
  `asc-ctl` 1.2.1 (sha256 `ff4539e7…9533`) is installed on 210 only.
- **Migrations 0015–0019:** additive and run in a single transaction, so a failure leaves the database at 0014.
  0018 refuses to run if a channel has two `live` sessions, and the pre-checks catch that first.
- **Order:**
  1. Preparation without downtime: record the current state, copy the code, build the images on 206 and ship
     them, then install `asc-ctl` and the env on 210.
  2. A window of about 15 minutes:
     - pre-checks on 212, then pause publishing;
     - stop the writers (206, then 201, then 210);
     - back up on 212, verified by gzip, row counts and an isolated throwaway restore;
     - start the API (which migrates), verify 0019, the indexes and that no old table lost rows;
     - start the workers (210, 206, 201), run the smoke checks, then unpause.
- **Rollback:** while the new image is still running, run `clipper migrate --downgrade 0014`, but only if there
  are no customer-owned rows. Then switch the tag back to 0.7.6. The 0.7.6 image cannot start on a 0019 schema.
  Restore the backup only if the downgrade fails or old data was lost.
- **Not part of this deploy:** the commercial service and payments, customer OAuth and real customer publishing,
  and SMTP unless it is already configured.
